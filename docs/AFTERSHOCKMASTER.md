### 6.2 เหตุผลที่ให้คนกระจุกในโซนอันตราย

**เชิงเกม:** ถ้ากระจายเท่ากันทุกโซน ผู้เล่นจะฟาร์มโซนเทาอย่างเดียวเพราะคุ้มที่สุด (0.59 คน/AP เทียบกับโซนแดง 0.05 คน/AP) โซนแดงจะไม่ถูกแตะเลย

**เชิงเนื้อหา:** โซนแดงคืออาคารถล่ม คนติดอยู่ข้างในเยอะ ส่วนโซนเทาคือบ้านเรือนเสียหายเล็กน้อย คนออกมาเองได้เกือบหมดแล้ว

### 6.3 ตัวแปรที่แต่ละโซนเก็บ

| ตัวแปร | ชนิด | ความหมาย |
|---|---|---|

**`trapped` ลดลงได้ 2 ทางเท่านั้น:**
1. ถูกช่วย (การช่วยสำเร็จ)
2. เสียชีวิต (ตายตามเวลา หรือตายเพราะช่วยได้ไม่ครบ)

## 8. ระบบ Action Point

### 8.1 แนวคิด

AP = **กำลังเสริมและทรัพยากรที่ทยอยมาถึง** ยิ่งสถานการณ์หนัก ยิ่งมีความช่วยเหลือหลั่งไหลเข้ามา

### 8.2 รายรับ (จ่ายทุก 1 ชั่วโมง = ทุก 2 ลูป)

```
AP ต่อชั่วโมง = 5 + โบนัส
```

| ผู้รอดที่หายไปแล้ว (ตาย+ช่วยแล้ว) | โบนัส | AP/ชม. |
|---|---|---|
| 0–20% | +0 | **5** |
| 20–40% | +1 | **6** |
| 40–60% | +2 | **7** |
| 60–80% | +3 | **8** |
| 80–100% | +4 | **9** |

**AP รวมทั้งเกมประมาณ 480 AP**

### 8.3 กฎ

- **AP สะสมได้ ไม่มีเพดาน** — กั๊กไว้บุกโซนแดงได้
- AP ไม่พอ → ไอคอนจางลง ลากไม่ได้
- **AP หักทันทีที่ปล่อยไอคอน** ไม่ใช่ตอนงานเสร็จ

### 8.4 ความย้อนแย้งที่ตั้งใจออกแบบ

> **ตอนที่มี AP มากที่สุด คือตอนที่แทบไม่เหลือใครให้ช่วยแล้ว**

ชั่วโมงแรก AP น้อย (5/ชม.) แต่คนรอดครบ 1,200
ชั่วโมงท้าย AP มาก (9/ชม.) แต่คนเหลือน้อยมาก

### 8.5 สมการความขาดแคลน

```
AP ที่จะเคลียร์ทุกโซน:
  27 โซนเทา × 6 AP   = 162
  13 โซนเหลือง × 18  = 234
  8 โซนแดง × 30      = 240
  ─────────────────────────
  รวม                = 636 AP (ยังไม่รวมบัฟ)
  + บัฟที่จำเป็น      ≈ 670+ AP

AP ที่มีจริง          = ~480 AP
→ ขาด                = ~190 AP (28%)
```

## 12. ระบบทอย 2 ชั้น

### 12.1 โครงสร้าง

```
จนท. ทำงานครบชั่วโมง
        ↓
┌─ ชั้นที่ 1 — ทอยสำเร็จ/ไม่สำเร็จ ────┐
│  roll = สุ่ม 1–100                  │
│  if roll <= อัตราสำเร็จ → สำเร็จ      │
└──────────────────────────────────────┘
        ↓
   ┌────┴────┐
   ↓         ↓
🟢 สำเร็จ   🔴 ไม่สำเร็จ
   │         │
   │         └─> ทอยอันตราย (ชั้นที่ 3)
   ↓
┌─ ชั้นที่ 2 — ทอยระดับความสำเร็จ ─────┐
│  ใช้ตารางประจำตัว OP                 │
│  → ได้ระดับ (สูงสุด/สูง/กลาง/ต่ำ)     │
│  → สุ่ม %ช่วยชีวิตในช่วงของระดับนั้น   │
└──────────────────────────────────────┘
```

### 12.2 ช่วง %ช่วยชีวิต (ใช้ร่วมกันทุก OP)

| ระดับ | ช่วง %ช่วยชีวิต |
|---|---|
| 🌟 สำเร็จสูงสุด | **99%** (คงที่) |
| ⭐ สำเร็จสูง | **90–98%** (สุ่ม) |
| ✦ สำเร็จปานกลาง | **70–89%** (สุ่ม) |
| ▪ สำเร็จต่ำ | **50–69%** (สุ่ม) |

### 12.3 ตารางระดับประจำตัว OP

| ระดับ | 👤 Robertson | 🐱 Lyla |
|---|---|---|
| 🌟 สูงสุด | **20%** | **35%** |
| ⭐ สูง | **25%** | **30%** |
| ✦ ปานกลาง | **35%** | **25%** |
| ▪ ต่ำ | **20%** | **10%** |
| **รวม** | **100%** | **100%** |

### 12.4 ผลลัพธ์เมื่อสำเร็จ

```
ช่วยได้   = floor(trapped × %ช่วยชีวิต)
เสียชีวิต = trapped − ช่วยได้        ← ที่เหลือตายหมด
โซน → เขียว (เคลียร์)
```

**ตัวอย่าง:** โซนมี 70 คน → สำเร็จระดับปานกลางที่ 78% → **รอด 54 คน · ตาย 16 คน** → โซนเขียว

### 12.5 ผลลัพธ์เมื่อไม่สำเร็จ

```
ช่วยได้   = 0
โซน       = สีเดิม (ยังไม่เคลียร์)
คนที่เหลือ = ยังตายต่อไปตามเวลา
→ ต้องส่ง จนท. มาช่วยใหม่
→ ทอยอันตราย (ดูหัวข้อ 13)
```

### 12.6 การแบ่งหน้าที่ที่สวยงาม

| สิ่งที่ตัดสิน | ตัวแปร | บัฟมีผลไหม |
|---|---|---|
| **สำเร็จไหม** | อัตราสำเร็จ | ✅ มีผล |
| **สำเร็จดีแค่ไหน** | ตารางประจำตัว OP | ❌ ไม่มีผล |

> **บัฟซื้อความแน่นอนได้ แต่ซื้อคุณภาพไม่ได้** → ต้องเลือกส่งคนให้ถูกงาน
> นี่คือสิ่งที่ทำให้ Robertson กับ Lyla ต่างกันจริง ไม่ใช่แค่ตัวเลขคนละชุด

### 13.1 หลักการสำคัญ

> **ทอยอันตรายเฉพาะเมื่อ "ไม่สำเร็จ" เท่านั้น**
> ถ้าสำเร็จ = ปลอดภัย 100% ไม่ต้องทอย

### 13.2 สูตร

```
โอกาสอันตราย = ค่าพื้นฐานโซน × (1 + ชั่วโมงปัจจุบัน ÷ 72)

เพดานสูงสุด = 50%
มี Alert → 0% เสมอ
```

### 13.3 ค่าพื้นฐานตามโซน

| โซน | ค่าพื้นฐาน |
|---|---|
| 🔘 เทา | **5%** |
| 🟡 เหลือง | **15%** |
| 🔴 แดง | **30%** |

### 13.4 ตารางโอกาสอันตรายตามเวลา

| โซน | ชม. 0 | ชม. 18 | ชม. 36 | ชม. 54 | ชม. 72 |
|---|---|---|---|---|---|
| 🔘 เทา | 5.0% | 6.3% | 7.5% | 8.8% | 10.0% |
| 🟡 เหลือง | 15.0% | 18.8% | 22.5% | 26.3% | 30.0% |
| 🔴 แดง | 30.0% | 37.5% | 45.0% | **50%** (ตัน) | **50%** (ตัน) |

> โซนแดงชนเพดาน 50% ตั้งแต่ชั่วโมงที่ 48

### 13.5 โอกาสบาดเจ็บจริง (รวมทั้ง 2 ชั้น)

```
โอกาสบาดเจ็บจริง = (1 − อัตราสำเร็จ) × %อันตรายพื้นที่
```

| สถานการณ์ | สำเร็จ | อันตราย | **บาดเจ็บจริง** |
|---|---|---|---|
| Lyla เดี่ยว → แดง (ชม.0) | 35% | 30% | **19.5%** |
| Lyla + Scan → แดง | 50% | 30% | **15.0%** |
| Lyla + Scan + Crowd → แดง | 75% | 30% | **7.5%** |
| Lyla ชุดเต็ม → แดง | 90% | 30% | **3.0%** |
| Lyla เดี่ยว → แดง (ชม.48+) | 35% | 50% | **32.5%** |
| Robertson → เหลือง (ชม.0) | 45% | 15% | **8.2%** |
| Robertson + Scan → เหลือง | 60% | 15% | **6.0%** |
| Lyla → เทา (ชม.0) | 80% | 5% | **1.0%** |

**ข้อดี:** บัฟช่วย 2 ต่อโดยอัตโนมัติ — เพิ่มโอกาสสำเร็จ และลดโอกาสบาดเจ็บไปพร้อมกัน สอนหลัก "เตรียมพร้อมก่อนลงพื้นที่" ได้ในตัว

**ข้อควรระวัง:** Alert (35 AP) ที่กันบาดเจ็บ 100% มีค่าน้อยลงมาก เพราะบาดเจ็บเกิดยากอยู่แล้ว — ต้องจับตาตอนทดสอบ

### 13.6 สองขั้นของการบาดเจ็บ

```
ปกติ ──ทอยติด──> 🩹 INJURED ──ทอยติดอีก──> 💀 LOST CONSCIOUSNESS
                      │                              │
                      └──รอ 3 ชั่วโมง──> ปกติ         └──รอ 4 ชั่วโมง──> ปกติ
```

| สถานะ | ผลกระทบ | ระยะเวลา | ส่งลงพื้นที่ได้ไหม |
|---|---|---|---|
| 🩹 **Injured** | อัตราสำเร็จ **−20** | ฟื้นเองใน **3 ชั่วโมง** | ✅ ได้ (เตือนแล้วให้ตัดสินใจเอง) |
| 💀 **Lost Consciousness** | **ทำอะไรไม่ได้เลย** | คูลดาวน์ **4 ชั่วโมง** | ❌ ไม่ได้ |

### 13.7 การแสดงผล

| สถานะ | การแสดงผล |
|---|---|
| Injured | ป๊อปอัพแจ้งเตือน + หยุดเวลา · ใช้ภาพ `-injured` |
| Lost Consciousness | **กากบาทแดง ✕ ทับไอคอน + รูปเป็นสีเทา** |
| คูลดาวน์ | **ตัวเลข** บนไอคอน จนท. |

## 15. ระบบคะแนน

### 15.1 สูตร

| รายการ | คะแนน |
|---|---|
| ช่วยผู้รอดได้ (Rescue) | **+1 ต่อคน** |
| ผู้รอดเสียชีวิต (Casualty) | **−1 ต่อคน** |

**ไม่มีแต้มลบจากการเสีย จนท.** เพราะ จนท. ไม่ตายถาวรแล้ว

### 15.2 ช่วงคะแนนที่เป็นไปได้

```
casualty = 1,200 − rescued
คะแนน = rescued − casualty = (rescued × 2) − 1,200
```

| ช่วยได้ | คะแนน |
|---|---|
| 0 คน | **−1,200** |
| 300 คน | −600 |
| 600 คน | **0** |
| 800 คน | +400 |
| 1,000 คน | +800 |
| 1,200 คน | **+1,200** |

### 15.3 หน้า Result

```

ผู้รอดชีวิตทั้งหมด      1,200 คน

─────────────────────────────────────
คะแนนรวม                            224

```
Robertson + Lyla → Lost Consciousness พร้อมกัน
        ↓

        ↓

## 23. Flow การส่งเจ้าหน้าที่

```
1. ผู้เล่นแตะไอคอน จนท. ค้างไว้
        ↓
2. ⏸ เกมหยุดเวลาอัตโนมัติ
        ↓
3. โซนที่ลงไม่ได้ขึ้นกากบาท ✕
   (ตามเงื่อนไข 8 ข้อในหัวข้อ 20)
        ↓
4. ลากไอคอนไปเหนือโซน
        ↓
5. แผงล่างเปลี่ยนเป็นข้อมูลอัตรา:
   ├─ ค่า AP
   ├─ อัตราสำเร็จ (แยกส่วน)
   └─ ความเสี่ยงบาดเจ็บ
        ↓
6. ปล่อยไอคอน
   ├─ บนโซนที่ลงได้ → ไปข้อ 7
   └─ ที่อื่น → ยกเลิก กลับข้อ 1
        ↓
7. หัก AP · ไอคอน จนท. ไปอยู่บนโซน · เริ่มนับเวลาทำงาน
        ↓
8. ▶ เกมเดินเวลาต่อ
        ↓
9. ระหว่างนี้:
   ├─ คนในโซนยังตายเรื่อย ๆ
   ├─ ผู้เล่นลงบัฟเพิ่มได้ (มีผลกับ จนท. ที่ลงไปแล้ว!)
   └─ ไอคอน จนท. แสดงเวลาที่เหลือ
        ↓
10. ครบเวลา → 🎲 คำนวณผล (หัวข้อ 19)
        ↓
11. แสดงผล:
    ├─ 🟢 สำเร็จ → โซนเขียว + คะแนนลอยขึ้น + Feed เขียว
    └─ 🔴 ไม่สำเร็จ → โซนสีเดิม + Feed แดง (+ ป๊อปอัพถ้าบาดเจ็บ)
        ↓

```

**Flow การลงบัฟเหมือนกันทุกประการ** ต่างกันที่:
- ลากไอคอน "สกิล" แทนไอคอนตัวละคร
- ยกเลิกไม่ได้หลังลงแล้ว (ไม่คืน AP)

# ส่วนที่ 7 — เทคนิค

## 31. การตัดสินใจทางเทคนิค

### 31.1 เทคโนโลยีที่ใช้

| ส่วน | ใช้อะไร | เหตุผล |
|---|---|---|
| โครงหน้า | HTML5 | มาตรฐานเว็บ ไม่ต้องติดตั้ง |
| หน้าตา | CSS (Grid + Flexbox) | จัดเลย์เอาต์ได้ยืดหยุ่น |
| ตรรกะเกม | JavaScript ล้วน | ไม่ต้องมี build step |
| แผนที่ | **SVG inline** | path กดได้ตรง ๆ · ซูมไม่แตก · ไฟล์เล็ก |
| Asset | **Base64 ฝังในไฟล์** | ไฟล์เดียวจบ · ไม่มีปัญหา asset ไม่โหลด |

### 31.2 ทำไมไม่ใช้เอนจิน

เกมนี้**ไม่มี**: ฟิสิกส์ · การชน · ตัวละครเคลื่อนที่ · อนิเมชันต่อเนื่อง · 3D · asset จำนวนมาก

**สิ่งที่เกมต้องการคือ: ปุ่ม + ตาราง + ตัวเลข + รูปที่กดได้** ซึ่ง HTML ทำได้ดีที่สุดโดยตรง

ถ้าใช้ Godot/Unity จะเสีย 2-3 วันกับ: เรียนระบบ node/scene · ตั้งค่า export เว็บ · แก้ไฟล์บิลด์ 15-20 MB · แก้ UI ที่ทำได้ยากกว่า HTML มาก

### 31.3 ทำไม SVG ไม่ใช่ Canvas

| | SVG | Canvas |
|---|---|---|
| กดโซน | ใส่ `onclick` ได้เลย | ต้องเขียนโค้ดตรวจพิกัดเอง |
| เปลี่ยนสี | แก้ `fill` | วาดใหม่ทั้งหมด |
| ซูม | ไม่แตก | แตกเมื่อขยาย |
| แผนที่ 48 โซน | เหมาะมาก | เสียเวลาโดยไม่จำเป็น |

### 31.4 ทำไมไม่ใช้ React

เกมอัปเดตทุกวินาที การ re-render ทั้งหน้าเปลืองกว่าการแก้ค่าตรง ๆ และ React ต้องมีขั้นตอน build เพิ่ม

### 31.5 แผนพอร์ตไป Godot (ทำทีหลัง)

โครงสร้างโค้ดจะแยกส่วนตรรกะกับส่วนแสดงผลชัดเจน:

| ส่วนใน JS | ตรงกับ Godot |
|---|---|
| `CONFIG` | ไฟล์ .gd ค่าคงที่ |
| `state` | autoload singleton |
| `tick()` | `_process()` หรือ Timer |
| `deploy()` | ฟังก์ชันเดียวกันเป๊ะ |
| `render()` | ตัดทิ้ง ใช้ signal แทน |

**ตรรกะ 90% ย้ายได้ตรง ๆ** ส่วนที่ต้องเขียนใหม่คือ `render()` อย่างเดียว

## 35. คำถามทางเทคนิค

### Q: HTML จะไหวไหมกับโปรเจกต์ขนาดนี้

**ไหวสบายมาก** — เกมนี้ต้องคำนวณตัวเลขไม่ถึง 500 ตัว อัปเดตวินาทีละครั้ง เว็บข่าวธรรมดาที่โหลดโฆษณา 20 ตัวทำงานหนักกว่าหลายเท่า

**ประโยคที่ใช้ตอบเพื่อนได้:**
> "เกมเราไม่มีฟิสิกส์ ไม่มีตัวละครเดิน ไม่มี 3D มันคือแผนที่กดได้กับตัวเลข ซึ่ง HTML ทำได้ดีที่สุดอยู่แล้ว ถ้าใช้เอนจินคือเอารถบรรทุกมาส่งจดหมาย"

### Q: HTML5 ใช้ได้ไหม

**ใช่ HTML5 คือสิ่งที่ใช้อยู่แล้ว** — เป็นชื่อเรียกมาตรฐานเว็บสมัยใหม่ ทุกอย่างที่เกมใช้อยู่ในนั้นหมด

### Q: ต้องมี Java ไหม

**Java กับ JavaScript คนละตัวกัน**

| ชื่อ | คืออะไร | ใช้ไหม |
|---|---|---|
| **Java** | ภาษาที่ต้องติดตั้งโปรแกรมแยก | ❌ |
| **JavaScript** | ภาษาที่อยู่ในเบราว์เซอร์ทุกตัว | ✅ |

JavaScript ฝังอยู่ในไฟล์ `.html` เดียวกัน ผู้เล่นเปิดลิงก์แล้วเล่นได้เลย

### Q: ต้องมี VS Code ไหม

**ควรมี** พร้อมส่วนขยาย **Live Server** (แก้ปัญหา CORS ตอนพัฒนา)

### Q: ทำไม asset ถึงไม่โหลด

**สาเหตุหลัก 3 อย่าง:**
1. เปิดไฟล์ด้วยการดับเบิลคลิก (`file://` โดนบล็อกเพราะ CORS)
2. ชื่อไฟล์ตัวพิมพ์ใหญ่-เล็กไม่ตรง
3. ชื่อไฟล์มีภาษาไทยหรือช่องว่าง

**วิธีแก้ที่ใช้:** **ฝัง asset ทั้งหมดเป็น Base64 ในไฟล์ HTML** → ปัญหาหายทั้งหมด

### Q: เอาขึ้นเว็บยังไง

**GitHub Pages** (ฟรี ไม่มีโฆษณา) หรือ **itch.io** (ลากไฟล์ขึ้นได้เลย)
จากนั้นทำ QR code แปะบนสไลด์

### Q: SVG ที่เป็น `<g>` ใช้ได้ไหม

**ใช้ได้ปกติ** — กดได้ เปลี่ยนสีได้เหมือน `<path>`
(สุดท้ายได้ไฟล์ที่เป็น `<path>` ล้วนแล้ว)
